# Review a2: performance across ASCII Animals

Brief `briefs/a2.md` at `ecc606d`. Reviewed `origin/meadow-t11` at `971a216`.

## Design

The largest everyday saving is to stop submitting desktop surfaces when the user cannot see them, then choose a
sustainable presentation rate for each exposed display. At 30 fps on the measured desk, the app writes about **1.50
GB/s of logical output pixels** before compositor reads, compression and physical display scaling. Even a complete
rewrite of the Meadow painter would save at most its measured **0.36 ms of CPU per pair of frames**, about **1.15
CPU percentage points** at the observed desk rates. A rewrite that keeps presenting the same fullscreen surfaces at
the same rate leaves the compositor with the same surface sizes and schedule.

The Meadow’s reported WindowServer excess is real in the recorded rows. Its cause remains open. Ground upload goes
from app memory to a Metal shader input. WindowServer receives the finished BGRA drawable, of the same size, format
and opacity as Ocean and Web. Meadow’s additional GPU texture read is measurable offscreen, but its extra upload is
too small to lead the investigation. The highest-value live comparison controls presentation rate, coverage, output
pixels and render load separately.

## What is missing?

- A per-display ledger of callback, skipped, encoded, completed and **presented** frames, with timing by stage and a
  display/session/visibility generation. The 3.1 energy logger samples commits. It cannot establish equal
  presentation cadence or attribution.
- A controlled compositor comparison. The earlier 60-second rows used one order and baseline WindowServer CPU
  drifted from 8.9% to 6.9%. There are no paired foreground-window, covered, battery or per-display power traces in
  that table. This review did no live testing. Offscreen GPU elapsed time, raw sizes and callback counts cannot
  establish WindowServer CPU, DRAM bandwidth, physical wake-ups or battery draw.
- A byte-for-byte suite spanning all three habitats and several consecutive frames per in-flight slot, with backing
  scale, theme, Calm, dissolve, geometry and input changes. At this commit `bench --digest` forces **Web**, and its
  digest omits `ground` and `hasGround` (`Sources/OceanTool/main.swift:194–197`, `Bench.swift:117–160`). I obtained
  `612a0c22c778b40b` in the default 900-frame Web run. Ocean’s pinned still and Meadow’s paint/ground/allocation
  checks are useful separate evidence.

### 1. Apply eligibility before scheduling work

**What happens now.** One mouse-transparent desktop-level window per AppKit screen joins all Spaces (`DesktopWindows.swift:52–63`). Once it has submitted its first frame, an occlusion event can stop that
display’s link. Full-screen apps and other Spaces are handled through the resulting window visibility, with no
explicit active-Space decision. A maximized app leaving an exposed strip can keep the full window, and thus the full
painter and drawable, live. The initial `!presented` exception treats a never-presented window as visible even after
an occlusion event. The workspace sleep signal is global. No drawing path checks per-display sleep or normalizes
mirror sets. AppKit may already give only the mirror leader. The code cannot cap duplicate work if two members are
enumerated. See `DesktopWindows.swift:82–110,125–137`, `OceanDirector.swift:55–91,148–199`,
`SystemSignals.swift:15–35`, and `OceanKit/Domain/SceneLayout.swift:29–46`. AppKit defines the visible bit by
partial window exposure and documents conservative behavior for some shapes. [AppKit
occlusion](https://developer.apple.com/documentation/appkit/nswindow/occlusionstate-swift.struct/visible?changes=_9&language=objc),
[Core Graphics display sleep and mirror
queries](https://developer.apple.com/documentation/coregraphics/core-graphics-functions?changes=_8_6).

**States and frequency.**

**Gain, risk and proof.** On the owner's desk, skipping a 33.3-fps external viewport saves 33.3 full submits/s and
about **0.49 GB/s** in logical output writes. In the CPU-only bench model its paint/pack/encode contribution is
about **0.13 Ocean / 0.55 Web / 0.80 Meadow** CPU points before shared scene work and driver overhead. If both
screens are truly invisible, eligible wallpaper submissions should be zero. The payoff for partial coverage and
WindowServer depends on real window stacking and should be measured. Use one display snapshot at launch/reconfigure
and mode changes with physical ID, logical render identity, scale, sleep/occlusion and active-Space facts. Treat the
mirror leader using Core Graphics and actual AppKit surface enumeration. Avoid polling window rectangles at render
rate or using the pointer router’s coarse rectangles to prove rendering is invisible. Risk is freezing an exposed
sliver, a paused look failing to update, or an animal jumping on wake. Verify a pure eligibility table and
per-screen counts through full-screen app, Space switch, opaque and translucent overlapping windows,
mirror/clamshell, one sleeping monitor, saver and lock. Run these live only under the manager’s supervised protocol.
Extend a1’s desktop visibility work. Let r1 finish its changes to `OceanDirector` and pointer routing first.

### 2. Isolate the WindowServer difference before optimizing for it

**Frame path and raw size.** Ocean updates its spatial hash, fish and sharks
(`OceanKit/Domain/World.swift:169–180,268–294,298–447,478–665`). It packs per-view shark geometry, headers, events
and a 4 B/cell fish grid. It runs zero to four cell-resolution wake passes (initial clear at least once), classifies
sharks and fish into RGBA8 cells, then expands wake, grid and atlas coverage at device resolution
(`OceanKit/Domain/FramePacker.swift:94–137,158–237`, `OceanKit/Render/OceanRenderer.swift:303–360`,
`Shaders.swift:54–115,361–420,505–641`). Web steps spiders, flies, silk and heat, then CPU paints blocks, glyphs and
overlays. Meadow steps breeze, flora, flight and the life story. It records many flower ops, shares breeze samples
across viewports at the same world time, paints touched cells and copies cached full-grid ground with per-frame
shadow/rim overrides (`OceanKit/Web/{WebWorld.swift:241–263,WebPainter.swift:493–553,626–658,926–949}`,
`OceanKit/Meadow/{MeadowWorld.swift:894–941,MeadowPainter.swift:379–403,720–787,943–970}`). Both canvas habitats
clear their arrays, replace five whole-grid textures, set a 64 B constant and compose with one fullscreen triangle.
Meadow adds a sixth whole-grid texture. The atlas, pipelines and viewport geometry are reused. The full target uses
`.dontCare` load and `.store`. `nextDrawable`, a Metal commit and presentation go through the same window path for
every habitat (`OceanKit/Render/{CellCanvas.swift:39–62,OceanRenderer.swift:167–179,202–284,287–296}`,
`OceanDirector.swift:95–141`).

**Where the compositor can differ.** Both the window and layer are opaque, with opaque black backing, no desktop
shadow, sRGB, BGRA8, framebuffer-only, two drawables, native backing scale. Initial layer fade is 0.8 s, before t8’s
settled samples. Every shader path, including clear and the dissolve, outputs alpha 1. Meadow’s ground RGBA alpha is
used inside the shader and never becomes layer alpha. There is no dirty rectangle supplied to Core Animation, no
persistent partially patched drawable, and no evidence here about the compositor’s private damage or compression
decisions. The main screen targets 3600×2338 and the external targets 2560×1440. At 30/33.3 that is **1.50 GB/s**
logical color stores, or **0.75 GB/s** at 15/16.7. These are estimates of uncompressed writes, independent of
content, and exclude compositor rereads. WindowServer can see different *pixels* and delivery times. Meadow’s
textured background and moving grass, ground shadows and glitter may change the distribution of pixels, compression
and damage if the compositor or hardware exploits those properties. Differences in independent desktop workload,
submitted versus presented cadence, or competition for GPU/memory service are also plausible. See
`DesktopWindows.swift:53–76,92–99,113–123`, `OceanKit/Render/OceanRenderer.swift:23,167–178,233–265` and
`Shaders.swift:449–463,675–705`. Apple's direct-to-display guidance concerns a full-screen game meeting specific
conditions. A desktop-level surface under icons and windows supplies no such guarantee. [Apple game-window
guidance](https://developer.apple.com/documentation/metal/managing-your-game-window-for-metal-in-macos?changes=l_4&language=objc),
[Framebuffer-only
drawables](https://developer.apple.com/documentation/quartzcore/cametallayer/framebufferonly?changes=_4).

**Measured ground isolation.** Two normal and two runs per alternative with the same moving scene, two screens and
600 measured 30-fps frames/screen per run. Normal ground upload alone took **about 0.005 ms CPU per pair**. Its raw
payload is **94,360 B per pair**, about **3.03 MB/s** at the recorded desk rates. Keeping the already-filled ground
in each slot (so shadows can go stale), while otherwise painting and shading normally, left the GPU medians at
**0.148–0.152 / 0.283 ms** versus **0.145–0.151 / 0.283 ms** normal. Bypassing the ground read while still uploading
reduced medians to **0.123–0.130 / 0.264 ms**. That is roughly **0.034–0.047 ms GPU per pair** once the comparable
endpoints are used. These interventions deliberately change pixels. The upload alone costs about **0.016 CPU
points** on the desk. This experiment gives a magnitude for app-owned work. It gives no live WindowServer
measurement.

**Change and proof.** First fix presentation instrumentation. In a later supervised run, interleave repeated
baseline/variant blocks, hold monitor mode and foreground/desktop coverage fixed, and compare medians and spread
across runs. Record presented counts, delivery jitter, app and WindowServer CPU, wake-ups, GPU counters and
footprint. Use three controls: present one identical frozen image once versus presenting those same pixels at a
fixed cadence. Present pre-rendered Ocean, Web and Meadow sequences at identical size, format and cadence. Vary
Meadow upload or shading cost while the final sequence stays the same (precomputed immutable ground
for upload, or a pre-rendered surface with equivalent offscreen work added separately). A flat-ground presentation
can then vary output texture while holding submission and other work fixed. If the gap follows presented pixels,
explore retained layers. If it follows cadence, scheduling takes priority. If it follows app GPU work with fixed
output, test graphics contention with GPU traces. If no reproducible gap persists, keep the common compositor path.
No pixel changes are needed for instrumentation. The live gap has no defensible percentage-point savings estimate
yet.

### 3. Give presentation a deadline and the simulation its own time owner

`DesktopWindows.swift:102–110` asks for a fixed min/max/preferred rate. At 100 Hz the current 30/15 requests deliver
around 33.3/16.7 in the energy log, approximately 11% over each target. `OceanDirector.swift:95–134` does simulation
before drawable acquisition on the live path, attempts acquire on main and registers a scheduled closure holding the
screen on every commit even though only first-frame work needs the hop. Failed acquires can spend sim time with no
output. `OceanRenderer.swift:130–139,215–218,316–319` waits for in-flight slots, and `main.swift:99–123` copies the
per-display commit dictionary into the test reader every five seconds. Production still mutates the per-display
dictionary each commit and never purges historical display keys. Occasional change logs in
`OceanDirector.swift:53–59,137–140,178–180,201–204` and one-time resource failures in `OceanRenderer.swift:248–271`
are separate from steady per-frame logging.

Choose callback eligibility, slot admission and deadlines before doing stale work. Keep per-scene monotonic
simulation and dissolve time, bounded snapshots and a real presentation acknowledgement. Use generation-tagged
callbacks only for initial/held work and timed sampling. Move an inappropriate workload out of a UI-critical queue
before tuning further. A shared scene already ignores old timestamps, but each accepted tick calls the clock. At 15
Hz × 1.5× one screen asks for six steps per callback with a ceiling of four. At 1×, a small delay can still discard
time. Clock and wake/held behavior need proof on mixed rates, including independent scenes. Ocean's wake uses
viewport-specific edge sampling, event sequence and multi-step history. Sharing a single rectangular wake makes seam
behavior change. Share invariant geometry/state and keep per-view wake semantics until approved
(`HabitatScene.swift:35–61`, `OceanClock.swift:13–31`, `Dissolve.swift:43–68,73–91`, `OceanRenderer.swift:305–359`,
`Shaders.swift:68–75`).

A 100-Hz display at a regular 25/14.29 fps uses one in four or seven refreshes and saves **25%/14% of the external
submits** versus 33.3/16.7. The corresponding logical output reduction is **123/35 MB/s**. A paced 30/15 average via
held refreshes is closer to the label, with uneven intervals on fixed 100 Hz. These are options to measure, with
smoothness and battery tradeoffs that need the director’s decision. For the 3.1.1 fix, measure
callback-to-present and drops first, remove gratuitous handler and stats overhead, and keep one bounded render
request per viewport. Verify no drift at 1×/1.5×, input latency under GPU load, no catch-up surprise on resume, and
consistent reveal when screens swap timestamp order. Count duplicate callbacks and uploads. A side-by-side with
`CAMetalDisplayLink` appears under architecture options. [Apple display-link
cadence](https://developer.apple.com/documentation/quartzcore/cadisplaylink), [Metal drawable-pool
guidance](https://developer.apple.com/documentation/metal/synchronizing-cpu-and-gpu-work).

### 5. Reduce redundant scene setup and still work

`main.swift:30–93` runs hand-over checks and crash/arrival state, initializes the Metal device/renderer
synchronously, creates the desktop host and starts it before building the menu and scheduling the greeting.
`OceanRenderer.swift:25–46` compiles one source string at runtime and synchronously creates four PSOs, even for a
Web or Meadow launch. `DesktopWindows.swift:45–88` eagerly creates viewport textures and rasterizes an Ocean atlas
for each screen. First frame latency also includes the first eligible display callback, first drawable, scheduled
fade and the 0.8 s fade to full opacity. Migration can synchronously wait on the other process and outrun all of
this, per `SharksHandover.swift:107–177` and a1. Keep the menu and session observers available when drawable setup
is deferred. Keep migration ownership with a1.

The instrumented desk setup measured **1.7–2.7 ms** for command queue, shader IR and four PSOs in already-warm
process launches, then roughly **6–9 ms** for Ocean and Meadow layout plus viewport and target creation vs **40 ms**
for Web. First paired encode through GPU completion added roughly **6–11 ms**. These intervals are inside the tool,

preserve it. A battery comparison for this app requires matching output and state on the same machine. [Apple

silk and one-pixel details. A 2× reduction in presentation frequency also halves logical color stores, with a larger
visible motion tradeoff. Interleaved per-layer render frequencies let flowers and ground move smoothly enough
without slowing wings, if the result is acceptable by eye. Compare Metal GPU time/counters and supervised energy at
several resolutions and rates. Inspect moving scenes in light and dark at 1× and 2×. Skip interpolation or
MetalFX if its extra pass/blur eats the savings on a simple 2D scene.

### F. Keep exact coverage atlases by default, trial distance fields only for many scales

**Build.** Share the existing 28-glyph R8 atlas by cell size, raster scale and the two distinct baselines. That is
small 3.1.1 resource work. For arbitrary magnification, an SDF/MSDF atlas would amortize rasterization and preserve
scalable outlines with GPU filtering. Keep the small-size raster atlas where its pixel fit matters, compare a hybrid
for zoomed previews first, and use the same glyph IDs. **Size medium, later only if arbitrary zoom/scale
proliferation materializes.**
`OceanKit/Render/{GlyphAtlas.swift:11–21,46–109,OceanRenderer.swift:150–160,266–274,Shaders.swift:505–510}`. [MSDF
research](https://dcgi.fel.cvut.cz/wp-content/wpallimport-dist/publications/pdf/publications-2018-sloup-cgf-msdf-paper.pdf).

**Expected gain, pixels and proof.** Current exact coverage costs roughly 34 KiB for each desk baseline and one-time
rasterization of 28 glyphs per key. An RGB distance field can use more memory than R8 and add fragment math. The
steady battery gain here is likely negligible. Exact atlas sharing saves rebuilds and memory with identical texels.
An SDF can change stem weight, dots, stroke sharpness and Chrome-compatible alignment. Compare actual atlas time,
bytes and glyph-pixel error under fractional scales and require the director's eye for changes.

### G. Compile shader IR at build time, and archive PSOs if cold startup warrants it

**Build.** Package a portable Metal IR library built from the same shaders, load the necessary pipeline family
first, and asynchronously prepare the others before the first switch or greeting that needs them. Then measure
GPU-specific `MTLBinaryArchive` support as an optional improvement, with a normal IR fallback and per-GPU/OS/build
validity. Metal 4 can harvest/serialize and build asynchronously on supported systems. The app has a macOS 14
baseline and a universal release build, and the offscreen SwiftPM tools must keep their own loader working. **Size
small–medium** for IR and lazy PSO creation, appropriate for 3.1.1 after measuring cold startup, **medium, later**
for multi-GPU archives and Metal 4 deployment. `OceanKit/Render/{OceanRenderer.swift:25–46,Shaders.swift}`,
`Package.swift:4–14`, `Tools/build.sh:24–34,44–61`, `.github/workflows/ci.yml:15–24`. [Apple Metal
libraries](https://developer.apple.com/documentation/metal/metal-libraries?changes=_8), [Apple binary
archives](https://developer.apple.com/documentation/metal/creating-binary-archives-from-device-built-pipeline-state-objects),
[Apple Metal 4 compilation](https://developer.apple.com/documentation/metal/using-the-metal-4-compilation-api).

**Expected gain, pixels and proof.** In already-warm launches the ceiling was only ~**2 ms** for the combined setup
stage, and a Web layout alone took ~40 ms. Cold first install gains are unknown. Keep Metal options and output bytes
identical at load, compare warm and genuinely cold first presented frame on oldest supported macOS/GPU and the desk,
and compare archive hit/fallback, bundled bytes and switch latency. Avoid moving compilation onto the first visible
switch.

### H. Use a system still or hardware-decoded loop where interactivity is optional

**Build.** An optional economy mode can keep the last good frame with the app’s system wallpaper integration and
wake only on explicit exposure/input rules. A second alternative is a pre-rendered HEVC loop using AVFoundation,
leaving arbitrary interactive animation when the user resumes. A video loop replaces simulation and packing with
hardware decode, but still produces full frames and can change grid, font, colors and character trajectories through
scaling/compression. It also loses live interactions in that mode. The system still can drop frame submission to
zero once installed. Use the public desktop still contract and r2’s restoration semantics. **Size medium** for a
held, on-demand opt-in policy, **large, later** for a video mode with color, transitions and device compatibility.
`ASCIIAnimals/SystemWallpaper.swift:44–102`, `OceanKit/Render/StillRenderer.swift:13–61`,
`ASCIIAnimals/OceanDirector.swift:55–91`. [Apple desktop wallpaper
controls](https://support.apple.com/guide/mac-help/choose-your-desktop-picture-mchlp3013/mac), [AerialWall native
playback](https://github.com/LeifsterNYC/AerialWall).

**Expected gain, pixels and proof.** A held system still can eliminate the full wallpaper render workload and its
repeated compositor submissions. A video mode can save much of the ~1–2% of one core spent in the offscreen CPU
pipeline on this desk, while leaving compositor traffic, decoding and a surface pool. Compare whole-system battery
energy, perceptual quality, installed disk space and wake-to-interaction latency with the existing live 15-fps mode
before pursuing. Desktop motion and interactions would be intentional changes requiring the director's decision.
