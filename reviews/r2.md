# r2 wallpaper recovery review

Verdict: changes requested

Reviewed `971a216..d9e05a0` against the trimmed brief.

## Findings

1. **Blocker — An upgrade can put a different picture on an old Space.** `Sources/OceanKit/Domain/WallpaperMemory.swift:129,138,152,168–171`. In a fake desktop, two 3.0 stills covered A on the same display. After upgrading, restoring the first Space put A back. Applying a new look on a third Space whose wallpaper was B let the keeper record B as the display's current original. Restoring the second legacy Space then put B there instead of A. Adoption keeps the old files but leaves their restore targets empty, so later restores consult a mutable display-wide original. Use the display key embedded in the legacy filename to snapshot the saved original into each record when adopting it. Preserve files with an unknown original and report that the original could not be recovered.

2. **Blocker — A failed directory read can make the app delete an in-use 3.0 still.** `Sources/ASCIIAnimals/SystemWallpaper.swift:148–150`, `Sources/OceanKit/Domain/WallpaperMemory.swift:168–173,243–246,315–319`. The real adapter turns a failed listing into an empty listing, which the keeper saves as a completed migration. When the folder is readable again, applying a new look can prune the older still even though another Space shows it. Uninstall can also interpret the empty migration as a clean restore. A fake directory read that failed once reproduced deletion. Distinguish a successful empty listing from an error, keep adoption pending, retry it before pruning and retain recovery on uninstall while adoption is unresolved.

3. **Should fix — Uninstall can discard the only original from ASCII Sharks.** `Sources/ASCIIAnimals/SharksHandover.swift:146–150`, `Sources/ASCIIAnimals/SystemWallpaper.swift:28–35`, `Sources/ASCIIAnimals/Uninstaller.swift:28–37,52–57`, `Sources/OceanKit/Domain/WallpaperMemory.swift:140,330–359`. When a Sharks still is left after handover and the copied Sharks memory is the only source of A, a failed restore on uninstall warns the user but only preserves the Animals key. Reinstalling loses A. A fake restore whose first set threw and whose reinstall had only the Animals memory reproduced a still left up with no restore target. If that Sharks still is on an unplugged display or hidden Space and there are no Animals records, the outcome can also claim success and discard the copy without warning. Carry forward the relevant Sharks recovery data and include unresolved legacy Sharks state in uninstall's retention decision. Also use the known Sharks original under a Sharks still when the display's Animals original came from a different Space. Lines 140 and 154 currently prefer that unrelated Animals image.

4. **Should fix — A force quit can strand a still before its recovery data is committed.** `Sources/ASCIIAnimals/SystemWallpaper.swift:38–41`, `Sources/OceanKit/Domain/WallpaperMemory.swift:249–254,281–285`, `Sources/OceanChecks/WallpaperChecks.swift:293–301`. The save callback queues an asynchronous UserDefaults write, then the keeper can change the desktop. If the process is killed before the first original reaches persistent storage, relaunch can adopt the file but has no original underneath it. The restart check passes an in-memory snapshot directly and cannot exercise that window. Acknowledge a successful durable write of the original and still record before setting the wallpaper, and skip the set if the write fails.

5. **Should fix — The set-error branch deletes the still before checking which image is selected.** `Sources/OceanKit/Domain/WallpaperMemory.swift:281–302`, `Sources/OceanChecks/WallpaperChecks.swift:136–139`. A fake set that selected the new still and then threw left the desktop pointing to a deleted file. The shipping fake only throws before writing. The real API's behavior for a partially successful set was not exercised. Read back even after an error, keep the file and record when the result is unreadable or otherwise uncertain, and discard only when there is enough evidence the file was never selected.

6. **Should fix — A pending uninstall alert leaves wallpaper callbacks active.** `Sources/ASCIIAnimals/main.swift:63–72,162–173,193–207`, `Sources/ASCIIAnimals/Uninstaller.swift:25–32`. When uninstall preserves the Stills directory and the warning alert stays up, a display or theme change with matching still on can schedule a new still during the alert's modal run loop. The app then exits through `exit(0)` after dismissing the alert, so the new still can remain. The restore cancels work that was already scheduled, but `isUninstalling` currently guards only the termination callback. Gate wallpaper refresh and reconcile once uninstall begins, or stop those callbacks before cleaning up.

### Open user-visible issues

1. **An access failure can still complete adoption as if the folder were empty.** `Sources/ASCIIAnimals/SystemWallpaper.swift:162` uses `fileExists` before listing. With a scratch Stills folder behind an inaccessible parent, Foundation returned false from `fileExists` while the same URL-based listing threw a permission error (Cocoa 257, underlying POSIX 13). The adapter would return an empty array, save adoption complete and never retry. Once access returns, a clean restore can delete a hidden, unrecorded 3.0 still, and uninstall can discard its recovery. Treat a confirmed missing directory as empty and let access errors reach the keeper.
2. **A restored legacy still can become a permanent recovery record after a transient read failure.** `Sources/OceanKit/Domain/WallpaperMemory.swift:382` restores visible legacy stills using the display original even when adoption is pending. In a one-display, one-Space fake with a known original, the first restore put A back with the listing failing. After the listing recovered, the next restore adopted the file left behind, reported one still left and kept recovery. There is no longer a Space to visit to clear that record. Carry the verified restore through the pending adoption or defer the restore until the listing succeeds.
3. **A successful Sharks restore can keep unrelated Animals stills indefinitely.** `Sources/OceanKit/Domain/WallpaperMemory.swift:373,417–427`, `Sources/ASCIIAnimals/Uninstaller.swift:34–42`. In a one-display, one-Space fake, directly restoring the only Sharks still put the original back. That restore and the next one both requested retention because the Sharks PNG was still on disk. Nothing in this flow retires it after a verified restore. This also blocks Animals still cleanup and makes uninstall retain the Animals Stills folder and warn about a Sharks picture. The note names the Animals folder, while the Sharks file lives in a separate Sharks folder. The on-disk rule is conservative for unseen Sharks references, but a verified restore alone cannot clear it. The report's caveat for a hidden Sharks reference whose file Sharks already removed remains as routed.
4. **The full-restore rule still relies on exclusive use of a still.** `Sources/OceanKit/Domain/WallpaperMemory.swift:350–369,417–427`. In a fake that explicitly gives two Spaces the same still URL, replacing it on the visible Space retained the file but dropped its record. Restoring that Space reported clean and deleted the file while the hidden Space still referenced it. Dropping the record also removes its exact original, leaving a later restore to fall back to the display's current original. This is a conditional macOS risk. The separate-account “Show on all Spaces” check must determine whether macOS can leave a second reference after one Space changes before relying on cleanup or uninstall's clean result.

### Disk use and route coverage

An offscreen sample through the wallpaper still renderer at 3600 × 2338 produced PNGs of about 0.33 MB for Ocean, 0.54 MB for Web and 0.71 MB for Meadow. Each successful refresh adds one per display until a restore reports clean. At ten refreshes per day on a display of that size, that is about 100–214 MB in 30 days. During active tweaking at one successful refresh per minute, it is about 20–43 MB per display per hour. Displays add their own files. The debounce groups nearby changes, and idle use with no refreshes adds nothing. Growth has no file-count or size cap. Long-running users, or users with a persistent recovery record such as the Sharks case above, can accumulate files through normal look and system appearance changes.

The standard fake checks still pass for quit/restore, matching off, reconnect after unplugging and relaunch with saved recovery. The app's launch, quit and matching-off entry points still call reconcile or restore as appropriate. With matching on, a Space switch alone still leaves its existing picture in place, as in 3.0. For unseen Spaces and detached displays the live recovery limits still apply. Settings contains exactly “Your own wallpaper comes back when you quit or turn this off.”
